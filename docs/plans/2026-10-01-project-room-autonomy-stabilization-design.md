# 운영실 협업과 자동 운영 안정화 설계

기준: [QA 수용 시나리오](../e2e/2026-09-30-project-room-autonomy-qa.md).
사용자가 해당 문서대로 동작할 때까지 개발과 안정화를 요청한 범위를 구현 기준으로 삼는다.
이 문서는 전체 구현 완료나 QA 통과를 선언하지 않는다.

## 현재 구조와 선택

현재 제품은 Room의 상하 관계, 대표 담당자와 orchestrator 전략, 개별 Task,
TaskBlocker, 반복 실행하는 Agent Goal, durable AgentTurn과 사용량 ledger를 갖고 있다.
반복 일정 자체와 한 번의 프로젝트 목표 실행을 구분해야 한다. 기존 반복 Goal의
`completed` 표시만으로 하위 작업·독립 QA·승인 상태를 검증할 수는 없다.

선택지는 기존 Task를 확장하여 실행 계약을 붙이는 방법, 별도 프로젝트 실행기를 만드는
방법, 모델 프롬프트만 강화하는 방법이다. 기존 전달·권한·재시도·알림 경로를 재사용하되
상위 실행 계약과 상태 전이는 서버가 집행하는 방법을 선택한다. 프롬프트만으로 승인,
취소, 반복·비용 한도와 완료 판정을 보장하지 않는다.

## 이번 안정화의 실행 계약

| 조건 | 서버·실행기 동작 | 사용자 표시 |
| --- | --- | --- |
| 담당자에게 상세 입력이 있음 | Task.spec를 assignment에 전달 | 제공된 경우 상세 보기 |
| 선행 작업 미완료 또는 실패 | claim·done을 차단하고 실패한 edge 유지 | 실패한 선행 작업과 필요한 조치 |
| 선행 작업 성공 | 결과 ID·본문·SHA-256·완료 시각을 저장하고 전부 만족 시 재개 | 결과와 출처 |
| 정기 실행이 입력 대기 중 | 새로운 동일 목표 실행을 대기 | 기존 대기 상태 유지 |
| 일정 비활성화·변경 또는 경쟁 실행 | 현재 일정과 정확히 맞는 CAS만 실행 | 오래된 트리거가 새 실행을 만들지 않음 |
| cron 시간대 지정 | IANA 시간대 검증 후 UTC 실행 시각 계산 | 실행 당시 시간대와 예정 시각 |
| 조용한 성공 | 큐에서 숨기되 결과·일정·중복 방지 키 보존 | 목표별 실행 이력에서 조회 |
| 완료 이벤트 재전달 | 영속 완료 마커로 횟수·상태 변경 중복 방지 | 같은 결과 유지 |
| 공용 담당자가 여러 프로젝트에 참여 | 입력은 room 폴더로 분리, 출력은 출처 project로 제한 | 관련 프로젝트의 자료만 표시 |
| 파일의 출처가 모호함 | 다른 프로젝트로 전달하지 않음 | 모호한 출력은 실행 로그에 원인 기록 |
| 방 전환·인증 변경 후 오래된 응답 도착 | 이전 응답·소켓 callback을 무시 | 현재 방의 최신 상태 유지 |

기존 flat shared 파일은 임의 삭제하지 않고 방 컨텍스트에서 제외한다. 현재 자료는 서버의
방별 backfill로 복원한다. 산출물은 `memory/outbox/<room_id>/`로 생성하도록 실행 지침을
갱신하며, 이전 형식은 활성 참여 방이 한 프로젝트로 명확히 결정될 때만 수용한다.

## 남은 전체 구현 범위

1. **상위 목표 실행과 연결된 작업 계약**: 운영실·프로젝트·최초 요청·입력 버전·허용 범위·완료
   기준·제한을 영속 저장한다. 위임은 상위 실행 아래 생성하며 목표, 입력 참조, 산출물,
   완료 기준을 담당 서브룸에 전달한다. 생성과 후속 변경은 입력 버전을 분리한다.
2. **운영실 중심 전달**: 하위 작업의 질문·결과·실패가 운영실에 task/version으로 연결된다.
   사용자는 운영실에서 답변하고 결과를 검토한다. 별도 서브룸 방문을 필수로 만들지 않는다.
3. **독립 QA와 자동 인계**: 연구→개발→QA의 입력·출력 버전을 추적하고 QA 실패의 재현 근거로
   수정 작업을 생성한다. 수정 후 해당 결함·관련 회귀를 재검증한다. 개발 담당의 완료는 QA
   통과와 구분한다. 필수 작업이나 필수 QA가 남아 있으면 상위 목표를 완료하지 않는다.
4. **질문과 승인**: 동일 질문 중복 방지, 부분 응답, 독립 작업 계속 진행, 답변 후 원래 작업
   재개를 서버에서 집행한다. 외부 동작 승인은 대상·내용·영향·산출물 버전에 연결하며
   미응답·거절·다른 버전의 승인은 실행 권한이 아니다. 테스트 수신처만으로 검증한다.
5. **통합 받은편지함과 알림**: 프로젝트·작업·유형·해결 여부를 한 화면에 모은다. 일반 진행은
   작업별 최신 상태로 묶고, 질문·승인은 별도로 남긴다. 이벤트 ID로 재전달 중복을 막는다.
6. **실패·변경·취소**: 오류 분류, 설정된 재시도 대기, 영속 시도 횟수와 마지막 정상 단계,
   변경 전후 입력·산출물 이력, 취소 후 신규 위임·모델 호출 차단을 구현한다. 이미 시작한
   처리의 취소 여부와 되돌릴 수 없는 효과를 상태로 보여 준다.
7. **상위 목표 한도**: 재시도·수정 라운드·위임 깊이·시간·사용량을 하위 작업과 재시도를 포함해
   합산한다. 호출 전에 예약·검사하며 한도 도달 후 추가 호출·위임을 시작하지 않는다.
   측정값·추정값·미수집값을 구분하고 미수집 비용을 0으로 표시하지 않는다.
8. **맥락 격리 보완**: 방별 파일 격리 외에 기존 에이전트 전역 notes와 모델 세션의 프로젝트
   경계도 확인한다. 공용 담당자를 지원할 때 한 프로젝트의 장기 기억이 다른 프로젝트
   프롬프트에 들어가지 않도록 저장·동기화·재접속 경로를 함께 다룬다.
9. **완료 보고**: 목표·결과·산출물·검증 근거·제한사항·다음 행동을 한 번 보고한다. 완료 후에는
   새 위임·추가 검토·불필요한 모델 호출을 차단한다. 출시 준비 완료와 미승인 출시를 구분한다.

## 검증과 판정

실제 시나리오는 운영 데이터와 분리된 두 프로젝트, 서로 다른 자료 표시, 가상 경력 자료,
테스트 저장소와 모의 제출·배포 수신처에서 실행한다. 알려진 결함으로 첫 QA 실패를
발생시키고 자동 수정과 독립 재검증까지 관찰한다. 초기 설정 이후 사용자 개입 횟수,
실제 모델 응답, task/turn/goal ID, 버전, 상태 전이, 산출물과 한도 집행 근거를 기록한다.

회귀 테스트와 브라우저 컴포넌트 검증은 해당 경로의 증거다. 이를 QA-01~21 또는 4개
종합 시나리오 전체의 통과로 확대 해석하지 않는다. 모든 기대 결과를 현재 상태에서
확인하기 전에는 전체 목표를 완료 처리하지 않는다.
