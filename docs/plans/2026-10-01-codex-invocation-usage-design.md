# Codex invocation usage from cumulative session counters

The actual QA15 execution `f575e5b5-3b43-4e91-9ec6-e97c1cbcda30` exposed a usage error: three lead invocations resumed one native handle and returned input counters213062,318383,430166. Each matches the native session's cumulative provider counter; summing them yields961611 instead of the observed session counter430166. Evidence is `.tmp/live-autonomy/qa15-native-usage-cumulative-session-readonly.json`. Existing ledger rows and the prior timeout/unknown outcomes remain historical facts.

The agreed implementation stores counter checkpoints in the SDK ReceiptStore, keyed by exact SessionScope and native handle. The manager already serializes a scope through one FIFO lock; terminal receipt and checkpoint update commit in the same local SQLite transaction. This avoids parsing mutable native log files for runtime billing and preserves existing native handle, generation, input-revision, and retry fences. An alternative was reading the session's token_count log before spawn, but that adds filesystem trust and parsing dependencies. Treating every CLI counter as invocation usage is the demonstrated bug.

Native Codex emits only bounded raw terminal counters and the actual observed thread handle internally. The store reports fresh counters from a known zero baseline or monotonic differences from a valid checkpoint. It retains the original counters, checkpoint, closed status, and SHA256 digests of handle/checkpoint identities in metadata. EngineTurn, room lifecycle, and the mirrored strict protocol models carry this metadata plus invocation counts. Missing cost remains null.

Missing terminal usage after an invocation starts durably invalidates the requested session checkpoint. The next complete terminal counter establishes a new checkpoint but that invocation's usage stays unknown; subsequent monotonic invocations can be measured. A missing legacy checkpoint, rollback, reset, changed/unobserved handle, invalid provider counters, or unconfirmed process also reports unknown rather than a negative or fabricated zero. Known not-started work does not invalidate a prior checkpoint. Non-Codex usage semantics are unchanged.

The change adds one SDK-local table, not a server migration. Existing usage/session/protocol/supervisor checks are run with only existing expectations adjusted; no new cases are authored. Actual acceptance requires a cold-loaded service and fresh real model workflow whose repeated native handle is compared against source counters, delivered deltas, and the server ledger. Root owns that reload and live scenario. No production ledger rewrite is authorized.
